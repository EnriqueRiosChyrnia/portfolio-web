Ryguasu

Inventory, sales, and point-of-sale SaaS for small retail in Paraguay — one backend serving many businesses.

Ryguasu ("hen" in Guaraní) is a multi-tenant SaaS for minimarkets, bakeries, and butcher shops: inventory with weighted average cost, a POS that freezes prices and costs at the moment of sale, multi-currency with frozen exchange rates, and an offline mode so the register keeps selling without internet. Every business shares one backend and one database, isolated by Row Level Security that fails closed: if the tenant context is missing, the query returns zero rows — never someone else's data.

Role · Backend & Infrastructure

I designed the data model and the architecture, implemented the backend, built the tenant isolation and the encrypted backup pipeline, and handle deployments and production verification. Frontend and visual design are teammates' work, built on top of my API contracts.

01Why Ryguasu exists

A minimarket or a butcher shop in Paraguay runs its inventory on paper or a spreadsheet: nobody knows the real cost of what's on the shelf, prices change with the exchange rate, and the till keeps no verifiable history. Enterprise POS systems are priced for supermarkets, not for a corner store.

Ryguasu is a subscription SaaS per branch with a 14-day trial: each business registers, loads its products (factory barcodes, internal codes, or scale PLUs), and sells from a web POS. The backend does the hard accounting so the owner doesn't have to.

Real costing, not guessesWeighted average cost recalculated on every purchase entry; margins come from real data.
Immutable sales historyEach sale line freezes price, cost, and product name at that moment. Changing a price never rewrites the past.
Multi-currencyGuaraní as base plus ARS/USD/BRL with per-business exchange rates, frozen into every sale.
Sells without internetOffline-first POS with an outbox: sales queue locally and sync when the connection returns.

02A modular monolith, on purpose

Backend in Java 25 with Spring Boot, organized as a modular monolith: packages by domain (auth, tenancy, products, inventory, sales, currency, reports, audit, subscriptions, offline sync) over a single PostgreSQL with versioned Flyway migrations. Not microservices, and that's deliberate: a sale must update stock and weighted average cost in one atomic transaction — splitting that over a network would buy complexity and give up correctness. The REST API is contract-first: the written spec is binding, and any endpoint that deviates must update the contract in the same commit.

Server-authoritative money

The client sends only productId and quantity. The backend computes and freezes price, cost, and name per line — amounts from the frontend are never trusted, and the sales history stays valid even when prices change. Money is numeric(19,4), never floating point.

03Tenant isolation that fails closed

42/42 isolated

All businesses share one schema; every tenant table carries a business_id. Isolation has two independent layers: the application resolves and enforces the tenant on every request, and underneath, PostgreSQL Row Level Security acts as a safety net that doesn't depend on application code being right. If a bug — or a background job that forgot its context — queries without a tenant, the database returns zero rows instead of everyone's data.

  • 001
    RLS from day oneEnabled when the schema had 6 tables, not 25: retrofitting row security onto a grown schema is where these projects usually fail. Every new tenant table ships its policy in the same migration.
  • 002
    No privileged shortcutThe application role has no superuser, no table ownership, and no BYPASSRLS — policies are FORCEd, so not even a bug in the app's own queries can step around them.
  • 003
    Verified adversariallyA test suite authenticates as tenant A and calls all 42 business endpoints with tenant B's identifiers: 42 of 42 come back 403. Isolation is proven, not presumed.

04Concrete backend details

  • 001
    Idempotency under real concurrencyEvery money or stock mutation requires an Idempotency-Key. The first check-then-insert version returned 500s under a genuine two-thread race — rewritten as INSERT … ON CONFLICT DO NOTHING and re-verified with the same race test: one movement, no error.
  • 002
    Pessimistic locking, fixed orderSELECT … FOR UPDATE on product and stock balance, always acquired in the same order — concurrent sales serialize cleanly instead of deadlocking.
  • 003
    Permissions down to the fieldA cashier never receives cost or profit fields: they're stripped from responses by permission, and profit reports return 403 outright. Role checks live at the endpoint and in the DTOs.
  • 004
    Rate limiting without RedisLogin throttling derived from the existing audit log with partial indexes — correct across N instances with zero new infrastructure. Progressive delay per account (an attacker can't lock a victim out) plus temporary IP blocks. Building it surfaced that the naive client IP was the proxy's — fixed with a shared resolver, without which the whole feature would have been useless in production.
  • 005
    Offline devices, signed identityA register syncing offline sales can't use a browser session, so each device holds a backend-signed license (JWT) carrying its tenant and a grace window by subscription state. The tenant context comes from the signature, never from client input — and a queued sale is never lost to an expired window.
  • 006
    Sessions over token pairsServer-side sessions stored in Postgres: instant revocation, correct across multiple instances, one HttpOnly cookie with a 12-hour rolling timeout sized to a full POS shift. Chosen over JWT access/refresh — and the deviation from the original spec is itself documented.

0549 decisions, written down with their why

Every significant choice is an ADR-style record: date, status, the decision, the reasoning, and which record supersedes it if it changed. Six months from now nobody has to reverse-engineer why the system is the way it is — the log answers it. When two specs contradict each other, the rule is to escalate to a human, never resolve silently.

The habit pays off in unexpected places: periodic spec-sync sessions compare the documents against the real code, and once even caught two inconsistencies inside the decision log itself.

Monolith over microservicesSale, stock, and cost form one transaction. Distribution would trade correctness for fashion.
Research before codeSupplier bonus units ("12+1 free") were resolved by reading the IAS 2 accounting standard and how SAP, Odoo, and NetSuite handle it — conclusion: the existing formula was already right. Zero code changed; one research doc written.
Billing modeled on the industryImmutable versioned plan prices (the Stripe pattern), payment snapshots, scheduled discounts — instead of a mutable price field that corrupts history.
Staff panel, separate appThe internal admin panel is a separate bundle on its own subdomain behind Zero Trust access — admin code never ships to customer browsers.

06The backup that earned its name

Restore tested

A nightly job dumps the database, compresses it, encrypts it with age public-key encryption — the private key never leaves the owner's machine — and ships it to Cloudflare R2 with checksums registered in the database. The working rule: an untested backup is not a backup. Getting there took four documented iterations.

v1 — pg_dump vs. forced RLS[FAIL] in production

pg_dump disables row security for consistency, and the production role — under forced RLS, with no bypass — rightly refused. The local end-to-end test had passed only because the local user was a superuser. First lesson made explicit: test against production privileges, not developer ones.

v2 — toggle with guaranteed restore[ OK ] complete or loud

The script discovers the forced tables dynamically, relaxes them for the dump, and re-forces them under a trap that runs even on failure — proven with injected errors and a kill -9. The app role keeps RLS at all times. The dump is complete, or it fails loudly; never silently filtered.

Dead man's switch[ OK ] Healthchecks.io

The job pings on success and on failure — and the absence of any ping is itself the alarm, which covers the case where the machine dies before reporting anything.

Real restore, from R2[ OK ] verified

Downloaded, checksum-verified, decrypted, and restored onto a clean PostgreSQL: 4,553 sales, 154 products, 3 tenants, all 25 RLS tables enabled and forced — zero manual fixes. That drill also exposed that dumps were missing their FORCE statements; now every dump appends them itself, so a restore is self-contained by construction.

The whole subsystem carries its own local test harness: 37/37 scenarios, including injected failures and full restore against a local S3.

07Small budget, production discipline

Everything runs on roughly USD 50 a month: the backend on Fly.io (São Paulo) with a managed PostgreSQL, and Cloudflare at the edge — DNS with strict TLS, Pages serving the frontend with a first-party /api/* proxy (no CORS, no third-party cookies), and R2 for encrypted backups. Memory was sized by measuring the real footprint, and the managed database was chosen over a cheaper self-run one deliberately: reliability of data over savings.

One environment until the first paying customer — with the requirement to stand up a separate staging before touching production after that, written down as a hard rule, not a good intention. Connection pooling runs in session mode because the tenant stamping requires it; the constraint is documented next to the config so nobody "optimizes" it into a data leak.

HostingFly.io (São Paulo) · managed PostgreSQL · a separate tiny machine wakes up nightly just to run the backup.
EdgeCloudflare DNS · Pages with /api proxy · R2 storage · Zero Trust access on the staff panel.
CI/CDGitHub Actions: full test suite with Testcontainers against a real Postgres, plus full-history secret scanning on every push.
CI earning its keepThe Linux runners caught a nanosecond-precision timestamp bug that never reproduced on macOS — an idempotency check that would have failed only in production.

08Practices that leave a paper trail

The codebase is one artifact; the discipline around it is the other. Specs are the source of truth, state documents record what's done and what's known to be broken, and production actions go through a human. This is what lets the project move fast without losing the thread.

  • [x]
    170+ backend tests — integration-heavy with Testcontainers against a real Postgres: adversarial cross-tenant suites, real two-thread race tests, RLS isolation checks.
  • [x]
    Security audit, verified dynamically — an independent audit produced 7 findings, each proven by actually executing the attack, and each tracked to closure. One outcome: a boot guard that aborts startup on default or missing secrets, before migrations can run.
  • [x]
    Spec-driven development — 35 specification documents as the single source of truth; the API contract is binding for every implemented endpoint.
  • [x]
    Living state documentation — a decision log (49 entries), an implementation log (44), and a known-issues register (16, most closed with full forensics) that any collaborator — human or AI agent — reads before touching anything.
  • [x]
    Bug forensics culture — one timestamp bug triggered a codebase-wide audit that found four more latent cases; the fix became a written convention plus a mandatory test assertion.
  • [x]
    Human in the loop — no push, no merge, no deploy without explicit human confirmation — a standing rule of the AI-assisted workflow, not an afterthought.
